# Правила командной разработки

Эти правила применяются ко всему репозиторию. В команде три участника.

## Git

- Сообщения коммитов строго в формате `<type>(<scope>): <short description>`.
- Допустимые типы: `feat`, `fix`, `refactor`, `docs`, `chore`.
- Пример: `fix(cart): validate cumulative quantity against fresh stock`.
- Не коммитить напрямую в `main` или `master` без явного указания пользователя.
- Для задач создавать ветки `feature/<имя-фичи>` или `fix/<описание-бага>`.
- Перед коммитом, push или обращением к пользователю за помощью с ними проверять `git status`, `git diff` и `git diff --cached`. Учитывать новые неотслеживаемые файлы отдельно.
- Не включать чужие изменения в свои коммиты. Делать небольшие тематические коммиты.
- Не добавлять `.env`, пароли, ключи API и другие секреты. Примеры настроек должны содержать только безопасные значения и пустые секреты.

## Границы модулей

Рекомендуемое разделение задач между тремя участниками (конкретных ответственных назначает команда):

1. API и данные: `app/ekt.py`, `app/catalog.py`, `data/`, `tests/test_catalog.py`.
2. Агент и корзина: `app/agent.py`, `app/cart.py`, `tests/test_agent.py`.
3. Интерфейс и демо: `static/`, инструкции демонстрации в `README.md`.

Общие контракты и интеграция: `app/models.py`, `app/config.py`, `app/main.py`, `app/uploads.py`, `tests/test_app.py`, зависимости. Изменять их точечно, заранее обозначая затронутые интерфейсы коллегам; не проводить несвязанные массовые рефакторинги.

## Бизнес-логика

- Комментировать сложные правила, особенно подтверждение корзины и проверку остатков; объяснять причину ограничения.
- ИИ может подготовить предложение, но не может подтвердить его от имени пользователя.
- Перед записью проверять свежие данные, привязку предложения к сессии, срок действия, цену и суммарное количество с учётом уже добавленного.
- Сохранять защиту от повторного и одновременного подтверждения.
- При изменении поведения запускать относящиеся к нему тесты; не утверждать, что непроверенные интеграции работают.
